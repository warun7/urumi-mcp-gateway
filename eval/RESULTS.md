# Tool-search evaluation

Generated by `eval/run.ts` against the live gateway on 2026-10-10. Catalog: **325 tools from 8 servers** (3 WooCommerce stores, the fetch server, the test servers, and a 288-tool synthetic SaaS farm).

## What the model has to read

| | tools/list | size | ≈ tokens (bytes ÷ 4) |
|---|---|---|---|
| full mode | 326 tools | 156.3 KB | 40,022 on every model call |
| search mode | 3 tools (`gateway__list_servers`, `gateway__search_tools`, `gateway__call_tool`) | 1.6 KB | 398 |
| + one `gateway__search_tools` result (5 tools with schemas) | | 2.7 KB avg | 692 per search |

Search mode cuts the standing tool context by **101×**. A turn that needs one search carries about 1,089 tokens of tool context instead of 40,022.

## Does search find the right tool?

Two task sets: **dev** (67 tasks, `tool-search.jsonl`), used while tuning the ranking, and **held-out** (35 tasks, `tool-search.holdout.jsonl`), written before any tuning and only ever looked at in aggregate. A task is a hit at *k* when an acceptable tool is in the top *k*; tasks that don't name a store accept that tool on any store. 0 tasks skipped (their store isn't provisioned here).

| | n | hit@1 | hit@3 | hit@5 | MRR |
|---|---|---|---|---|---|
| **gateway search**, dev | 67 | 69% | 75% | 81% | 0.74 |
| **gateway search**, held-out | 35 | 63% | 80% | 89% | 0.73 |
| keyword baseline, dev | 67 | 49% | 69% | 79% | 0.59 |
| keyword baseline, held-out | 35 | 43% | 60% | 83% | 0.55 |

The baseline ranks tools by how many of the query's words appear in their name and description: what a quick grep would do.

**Gateway search on the dev set, by kind of task**

| | n | hit@1 | hit@3 | hit@5 | MRR |
|---|---|---|---|---|---|
| paraphrased (avoid the tool's own words) | 29 | 55% | 62% | 66% | 0.61 |
| store tools (several stores expose the same tools) | 17 | 76% | 76% | 76% | 0.77 |
| 288-tool synthetic SaaS farm | 41 | 59% | 68% | 78% | 0.67 |

Search latency through the full MCP path (client → Traefik → gateway → index → client): p50 7 ms, p95 18 ms.

## How the ranking got here

The first version was plain BM25 (MiniSearch, name boosted 3×, prefix matching). The eval showed it **losing to the keyword baseline** on the dev set, and the miss list said why: BM25 is blind to the verb. "Start a performance review" scored `create_review`, `update_review` and `delete_review` the same (they share the noun), and ties fell to whichever came first, sometimes a delete.

| version | dev hit@1 | dev hit@5 | dev MRR | held-out hit@1 | held-out hit@5 | held-out MRR |
|---|---|---|---|---|---|---|
| v1: BM25 | 42% | 77% | 0.55 | 51% | 83% | 0.63 |
| v2: + light stemming, action-aware re-rank, read-before-write | 67% | 79% | 0.72 | 63% | 89% | 0.73 |
| v2, after fixing woo-mcp's `sales_summary` description (it returned the average order value without saying so) | 68% | 80% | 0.74 | 63% | 89% | 0.73 |
| v2.1: past-tense questions aren't write requests; "how much / total / average" prefers summary tools (found by the e2e suite; its query joined the dev set) | 69% | 81% | 0.74 | 63% | 89% | 0.73 |

v2 changes, all generic rather than per-query:
- **Stemming** on both sides ("couriers" finds "courier", "scheduled" finds "schedule"), replacing prefix matching.
- **Action-aware re-rank.** Tool names are almost always verb_noun, so each tool's verb is read from its name and the query's intent from its action words ("add", "start", "set up" → create; "cancel", "mark", "turn off" → update; "remove" → delete; "find" → search). Matching verbs are boosted, mismatched writes demoted.
- **Safe defaults.** Without a write intent, read tools outrank writes and deletes rank last; a record id in the query ("order 77") favours `get_*` over `list_*`.
- Function words ("did", "get", "we") are no longer search terms, so "how many orders did we get" stops matching every `get_*` tool.

The held-out set moved the same way as the dev set, so these are not tuned to the dev queries. With 35 to 67 tasks, one task is 1.5 to 3 points: read differences of a few points as noise.
`apps/gateway/test/search-eval.test.ts` runs this evaluation offline against `catalog.snapshot.json` in CI and fails if either set drops below its floor.

## Where it still struggles (dev set, not in the top 5)

- "how much money did we make yesterday": wanted `acme__sales_summary` / `initech__sales_summary` / `woo__sales_summary`; got `farm__billing_search_refunds`, `farm__billing_list_refunds`, `farm__billing_get_refund`
- "add a new item to the shop for 499 rupees": wanted `acme__create_product` / `initech__create_product` / `woo__create_product`; got `farm__inventory_create_stock_item`, `farm__inventory_get_stock_item`, `farm__inventory_delete_stock_item`
- "is the blue mug in stock": wanted `acme__list_products` / `initech__list_products` / `woo__list_products`; got `farm__inventory_get_stock_item`, `farm__inventory_search_stock_items`, `farm__inventory_list_stock_items`
- "what does the shop sell": wanted `acme__list_products` / `initech__list_products` / `woo__list_products`; got nothing
- "post an announcement in the general channel": wanted `farm__chat_create_message`; got `farm__chat_create_channel`, `farm__chat_get_channel`, `farm__chat_search_channels`
- "remind me tomorrow at 9 to call the supplier": wanted `farm__chat_create_reminder`; got `farm__chat_get_reminder`, `farm__inventory_get_supplier`, `initech__get_store_info`
- "is Ravi online right now": wanted `farm__chat_get_user_status` / `farm__chat_list_user_statuses` / `farm__chat_search_user_statuses`; got nothing
- "schedule a meeting with the design team on Friday": wanted `farm__calendar_create_event`; got `farm__chat_create_reminder`, `farm__chat_search_reminders`, `farm__chat_list_reminders`
- "reorder more stock from our vendor": wanted `farm__inventory_create_purchase_order`; got `farm__inventory_get_stock_item`, `farm__inventory_search_stock_items`, `farm__inventory_list_stock_items`
- "print a shipping label for order 1001": wanted `farm__shipping_create_label`; got `farm__shipping_get_label`, `acme__get_order`, `initech__get_order`
- "a customer wants to send an item back": wanted `farm__shipping_create_return`; got `farm__inventory_create_stock_item`, `farm__inventory_get_stock_item`, `farm__inventory_delete_stock_item`
- "roll out version 2.3 to production": wanted `farm__devops_create_deployment`; got `farm__devops_get_incident`, `farm__devops_search_incidents`, `farm__devops_list_incidents`
- "the site is down, declare an outage": wanted `farm__devops_create_incident`; got `farm__devops_search_incidents`, `farm__devops_list_incidents`, `acme__sales_summary`

These are vocabulary gaps: "money" vs "revenue", "shop" vs "store", "roll out" vs "deployment", "online" vs "presence". Word matching can't bridge them. The next step is hybrid retrieval: embed each tool's text once per catalog change and fuse vector ranks with these BM25 ranks (reciprocal rank fusion). BM25 stays in the loop because exact names and identifiers ("SKU", "A/B") are where embeddings are weakest.

## Notes

- Hit@5 matters more than hit@1 in practice: the model reads all five results with their descriptions before picking, and it can search again with other words.
- Search runs after the permission filter, so a member is never shown (and the model never tempted by) a tool they can't call.
- Reproduce: `make eval` (live, refreshes the snapshot) or `make eval-offline` (no cluster needed).
